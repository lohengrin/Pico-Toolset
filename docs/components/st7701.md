# st7701

RGB-parallel ST7701S LCD driver for the Presto's 480x480 panel (RP2350 only).
The panel is scanned out continuously by PIO + DMA from a framebuffer in SRAM,
so it has its own small API instead of implementing
[`DisplayPanel`](driver-interfaces.md) (no windows, no pixel streaming).

## Config -- `St7701Config`

No field has a default (all board wiring).

| Field | Notes |
|---|---|
| `width`, `height` | 240 (every pixel and line doubled by scanout, 115 KB) or 480 (450 KB) |
| `rotate_180` | only 0/180 possible |
| `pin_d0` | first of 16 consecutive RGB565 data pins; `d0+16`, `d0+17` driven low |
| `pin_hsync`, `pin_vsync`, `pin_de`, `pin_dot_clk` | |
| `spi`, `pin_spi_cs/clk/dat` | 9-bit init SPI at 8 MHz; CS is a plain GPIO |
| `pin_backlight` | PWM (wrap 6200); `0xFF` = none |
| `pio` | the driver claims 2 state machines and the whole IRQ0/IRQ1 pair |
| `framebuffer` | caller-owned, SRAM, 4-byte aligned: `width*height` `uint16_t` (Rgb565), `width*height` `uint8_t` (Palette8), unused (Scanline565) |
| `format` | `Rgb565` (default), `Palette8` or `Scanline565` -- see below |
| `line_callback`, `line_user` | Scanline565 only |
| `visible_height`, `blank_index` | `visible_height` (0 = `height`) is the number of source lines backed by pixels; the lines below are scanned out as a black band from one static line, so the framebuffer is `width*visible_height` (480x300 Palette8: 144 KB instead of 225 KB) and a `Scanline565` callback is never called past it. `St7701::height()` returns the visible height. In `Palette8` the band shows palette entry `blank_index` (default 0), so it follows that entry's colour |
| `top_blank_lines` | (Rgb565 / Palette8 only) source lines scanned out as the same black band *above* the framebuffer, so a smaller picture can sit centred without paying for the surrounding lines: 480x320 centred in 480x480 is `top_blank_lines = 80`, `visible_height = 320` (a 300 KB RGB565 framebuffer, 80 black lines above and below). Clamped to `height - visible_height`; ignored for `Scanline565`. The framebuffer starts at panel line `top_blank_lines` |
| `max_pixel_clock_hz` | dot-clock ceiling, 0 = 34 MHz. The divider rounds up from `clk_sys`, so the real clock is at or below it. Lowering it lengthens each line (21 us at ~25 MHz, ~28 us at ~19 MHz, 33 us at ~16 MHz for 480 wide) and slows the refresh, which gives a `Scanline565` callback more time; the panel's minimum accepted dot clock is not documented, so lower it gradually |

## Pixel formats

| Format | SRAM for pixels | Notes |
|---|---|---|
| `Rgb565` | 115 KB (240x240) / 450 KB (480x480) | `st7701_encode()`d pixels; `present()` copies a frame tear-free |
| `Palette8` | 56 KB / 225 KB | one byte per pixel indexing a 256-entry table (1 KB, internal, 1 KB-aligned); uses 3 state machines, 4 DMA channels and all 18 data pins; at width 480 the pixel divider is forced to >= 8. `set_palette_colour(i, r, g, b)` (table starts as RGB332), `present8()`. A colour cycle needs no pixel writes. Fewer colours, so gradients and photos need dithering |
| `Scanline565` | ~4 KB (line ring inside `St7701`) at any size | no framebuffer: `line_callback(y, line, user)` renders each line into a 4-line ring up to 2 lines ahead of the beam. `scanline_task()` must run in a loop on the scanout core (`while (true) lcd.scanline_task();` on core1). The callback has about one line time (~20-30 us at full res), runs in thread context (not an interrupt) and should live in RAM (`__not_in_flash_func`, data in SRAM). `missed_frames()` / `late_lines()` report deadline misses. A frame is started only if line 0 is ready inside the vertical blanking interval, otherwise it is skipped (black) |

The callback must average less than one line time: filling 480 pixels pixel-by-pixel with a divide per pixel already overran it at the default clock. Copy pre-rendered lines with 32-bit moves (as `st7701_scanline_example` does) or lower `max_pixel_clock_hz`. If the callback is too slow the symptom is stale lines and `late_lines()` climbing.

`Scanline565` suits tile/sprite/text renderers; it does not suit code that draws
arbitrary pixels, and LVGL-style full-frame flushes do not fit its pull model.

**Status:** all three formats are validated on the Presto (`Palette8` via
`st7701_palette_example` / `PRESTO_PALETTE`, `Scanline565` via
`st7701_scanline_example`). The per-line timing figures above are estimates, not
measurements.

## API -- `St7701`

- `bool init(cfg)` -- SPI init sequence (~0.4 s), then PIO timing/pixel SMs, DMA
  and interrupts. The scanout interrupts are served by the **calling core**; call
  from core1 to keep scanout independent of core0 stalls. False when no free SM/DMA.
- `framebuffer()` / `framebuffer8()`, `format()`, `width()`, `height()`.
- `present(src)` -- Rgb565: copies a full frame behind the scan position (tear-free). `present8(src)` -- Palette8 (waits for vblank, then copies).
- `wait_for_vsync()`, `display_row()` (beam row, for starting a copy inside the blank band below `visible_height` without waiting for a whole vblank), `set_backlight(0-255)`, `cleanup()`.
- `st7701_encode(rgb565)` -- the pixel format is RGB565 with the **two bytes
  swapped** (the DMA swaps them back).

## Notes

- Pixel clock is capped at 34 MHz from `clk_sys`; full-res runs the pixel SM at
  twice the timing SM's rate.
- Only one instance can exist; the interrupt handlers reach it through a
  file-scope pointer.
- `St7701Driver` (libs/screen) draws into Rgb565 and Palette8 (RGB332) buffers; it ignores drawing calls in Scanline565.
- The `St7701` object contains the 4-line ring (~3.8 KB) in every format.

Lineage: Pimoroni's Presto ST7701 driver (MIT, Michael Bell and Phil Howard),
without PicoGraphics/MicroPython; PIO programs (including the palette decoder)
vendored unchanged. `Scanline565` is new in this repo.
- **RP2350-E5 (DMA abort)**: the line DMA channel is chained to a re-arm channel, so aborting it
  has to clear the enable bit of both first (`abort_chained_dma()`); otherwise the abort can race
  the chain, never complete, and the scanout interrupt spins forever on its core (black screen,
  main loop stuck in `present()`/`flush()`). Seen with heavy Bluetooth traffic, which shifts
  interrupt timing; fixed after the A2DP bring-up on the Presto.
